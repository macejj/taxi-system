# 城市出租车运营管理与决策支持系统

> 毕业设计项目 · 由「出租车资料管理系统」升级为
> **运营管理 + 数据分析 + 需求预测 + 调度决策支持** 四位一体的运营决策系统

---

## 一、项目定位与升级说明

原系统只实现了车辆、驾驶员档案的增删改查与一个简单的收入统计折线图，
本质上是一个**资料管理系统**。本次升级围绕「让数据产生决策价值」重构了整个系统：

| 层次 | 升级前 | 升级后 |
| --- | --- | --- |
| 数据模型 | 4 张表（车辆、驾驶员、绑定、订单） | **12 张表**，新增区域、叫车需求、预测结果、调度方案、调度指令、系统参数等 |
| 运营管理 | 车辆/驾驶员 CRUD + Excel 导入 | 区域网格、车辆全生命周期（保险/营运证/保养到期提醒）、驾驶员资质与绩效、人车绑定排班、**叫车需求（含未满足）与营运订单双数据源**、订单增删改查与导入导出 |
| 数据分析 | 1 个收入折线图 | **14 类分析**：KPI 与环比、收入趋势（时/日/周/月）、24 小时供需匹配、星期分布、星期×小时热力图、区域热度排行与雷达对比、里程利用率、驾驶员绩效、车辆效率、支付方式、天气影响、异常预警 |
| 需求预测 | 无 | **5 个模型 + 滚动原点回测自动选优**：季节朴素法、季节移动平均、阻尼趋势 Holt-Winters 三次指数平滑、多元线性回归、逆误差加权组合模型；输出未来 1~168 小时逐时需求与 95% 置信区间 |
| 调度决策 | 无 | **供需缺口测算 + 最优指派**：区域×时段需求估计、运力盘点、边际收益递减的调度收益建模、**匈牙利算法（O(n³)）与贪心策略双实现并对比**、调度单下发/执行反馈/效果评估 |
| 工程化 | 硬编码数据库口令、无依赖清单 | `.env` 配置化、`requirements.txt`、建库与造数脚本、**引擎单元测试 + 66 项接口冒烟测试**、操作日志审计、参数在线配置 |

### 1. 运营驾驶舱
今日订单/收入/满足率/空驶率（含较昨日环比）、车队概况、近 6 小时实时供需、
近 N 天收入与订单趋势、24 小时需求—运力匹配、区域收入排行、运营预警分级列表、
快捷入口、数据健康度。60 秒自动刷新。

### 2. 运营数据分析（5 个标签页）
- **运营总览**：8 项 KPI + 环比、收入趋势（日/周/月）、支付方式环形图、里程利用率仪表盘
- **时段与区域**：24 小时供需分布、星期分布、星期×小时热力图、区域排行表、区域雷达对比
- **驾驶员绩效**：评分/订单/收入/空驶率/综合得分排行 + TOP10 收入柱状图
- **车辆效率**：里程—收入散点图、状态分布饼图、每公里收入排行
- **异常预警**：按等级筛选与搜索的预警明细

### 3. 叫车需求分析
需求侧（叫车请求，**包含未被满足的需求**）的多维可视化：
小时供需匹配、星期×小时热力图、区域需求对比、**区域×时段需求矩阵**、星期分布、天气影响。

### 4. 需求预测中心
- 区域可选「全域」或任一功能区，预测未来 24/48/72 小时
- 展示最优模型、回测指标、**5 个模型的误差对比表与柱状图**
- 历史实际值 + 未来预测值 + 95% 置信区间同图展示
- 预测准确率评估（预测目标时刻真实值回填后对比）
- 历史预测批次查询与明细回溯

### 5. 调度决策中心（4 个标签页）
- **供需态势**：区域×时段预测需求、可用运力、折算运力、供需缺口、缺口等级、预期增收
- **生成调度方案**：贪心 / 匈牙利双策略、策略对比、调度指令清单、**24 小时策略对比实验**与**随机算例基准实验**
- **调度方案管理**：方案列表、详情、状态流转
- **执行与效果评估**：调度单执行反馈、实际增收与预期增收对比、准确率

### 6. 运营管理
营运订单（多条件查询/汇总/增删改/Excel 导入导出/模板下载）、
车辆档案（含到期提醒、绑定驾驶员、状态流转）、
驾驶员档案（身份证脱敏、评分、资质到期）、
人车绑定排班（白班/夜班/全天，同车同班次最多 2 人）、
运营区域（功能区网格、中心坐标、需求强度）。

### 7. 系统管理
用户与角色（admin/operator/viewer）、**19 项业务参数在线配置并实时生效**、
操作日志审计（自动记录所有写操作）、数据维护（数据量统计、**一键生成可复现的仿真数据**、分级清空数据）。

## 三、技术栈

| 层次 | 技术选型 |
| --- | --- |
| 后端框架 | Python 3.11+ / FastAPI 0.110+ / Uvicorn |
| ORM | SQLAlchemy 2.0 |
| 数据库 | MySQL 8.0（可通过 `.env` 切换为 SQLite） |
| 认证 | JWT（python-jose）+ bcrypt（passlib） |
| 数据分析 | pandas、numpy、openpyxl |

| UI 组件 | Element Plus 2.8+（含图标） |
| 图表 | ECharts 5 |
| 请求库 | axios |

> **为什么不用 scikit-learn？** 系统中的 Holt-Winters 三次指数平滑、多元线性回归、
> 滚动原点回测、匈牙利指派算法均为手工实现，算法原理完全可控、可写入论文，
> 且避免了 Python 3.14 环境下重型科学计算库的安装与兼容风险。

## 五、快速开始

### 5.1 环境要求

- Python 3.11 及以上
- Node.js 18 及以上
- MySQL 8.0（或改用 SQLite）

### 5.2 后端

```bash
cd backend

# 1) 安装依赖
pip install -r requirements.txt

# 2) 配置数据库（可选，默认 root/123456789@localhost:3306/taxi_db）
copy .env.example .env      # Windows
# cp .env.example .env      # macOS / Linux
# 编辑 .env 修改 DB_USER / DB_PASSWORD / DB_NAME

# 3) 建表 + 初始化账号与参数
python scripts/init_db.py

# 4) 生成仿真运营数据（默认近 60 天 / 60 台车 / 80 名驾驶员，约 1~2 分钟）

python -m uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

## 六、仿真数据说明

`backend/scripts/seed_data.py` 会生成一套**可复现**（固定随机种子）且**有业务规律**的运营数据：

- **10 个功能区**：火车站广场、二七商圈、会展中心、高新技术开发区、大学城、滨河新城、
  老城区、国际机场、人民公园景区、市第一人民医院，坐标集中在一个约 10km × 10km 的城区内。
- **每个功能区有独立的出行作息曲线**（如居民区早高峰、商圈晚高峰、景区白天为主、
  工业区通勤双峰），因此同一时刻既有运力紧张的区域、也有运力富余的区域 ——
  这正是跨区调度真实存在的价值来源。
- **需求生成**：以泊松过程逐小时抽样，并叠加日周期、周周期、天气因子（雨雪天需求上升）、
  节假日因子与缓慢增长趋势。
- **运力与满足率**：驾驶员分白班/夜班/全天，只有**在岗车辆**才计入运力；
  需求规模会自动标定，使全城平均负荷率约为 0.85，
  于是**平峰期满足率约 95%+，早晚高峰落到 60% 左右**，形成真实的供需缺口。
- **数据规模**（默认参数）：约 **7.8 万条叫车需求 / 6 万条营运订单**，
  单均金额约 **26 元**，单车日均营收约 **420 元**，满足率约 **75%**。

重新生成数据：

```bash
# 命令行
python scripts/seed_data.py --days 90 --vehicles 80 --drivers 100

# 或在系统「系统管理 → 数据维护」页面上一键生成
```

## 七、核心算法速览

### 7.1 需求预测（`services/forecast.py`）

1. 把叫车请求按「区域 × 小时」聚合成等间隔序列，缺失小时补 0。
2. 构造特征：小时哑变量、星期哑变量、高峰标记、节假日标记、雨天标记。
3. 五个模型并行训练：

   | 模型 | 原理 |
   | --- | --- |
   | 季节朴素法 | ŷ(t) = y(t − 168)，直接取上周同一时刻 |
   | 季节移动平均 | 同小时最近 3 周需求的算术平均 |
   | Holt-Winters | 水平/趋势/季节三重指数平滑，**带阻尼趋势**，平滑系数与加法/乘法模式网格寻优 |
   | 多元线性回归 | 最小二乘，含趋势项、23 个小时哑变量、6 个星期哑变量、高峰/节假日/雨天 |
   | 组合模型 | 以回测 RMSE 的倒数为权重加权平均 |

4. **滚动原点回测**：以历史末端为原点向前滚动 3 折，每折从原点**直接**预测未来 168 小时。
   所有模型只允许使用预测原点之前的数据（测试中用「篡改预测窗口数据后预测值不变」来验证无前视泄露）。
5. 按 RMSE（对高峰误差更敏感）选优，在全量数据上重训后预测未来 horizon 小时，
   并以回测残差标准差给出近似 95% 置信区间。

### 7.2 调度决策（`services/dispatch.py`）

1. **需求估计**：按「区域 × 星期 × 小时」取近 4 周同星期同时段历史均值，乘近期趋势修正系数。
2. **运力盘点**：以车辆常驻区域统计可用运力，扣除已下发未执行的调度车辆，再按单车小时服务能力折算。
3. **缺口测算**：`缺口 = 预测需求 − 折算运力`，正值为缺口区域，负值为盈余区域。
4. **收益建模**：同一区域每多调入一辆车，可承接的缺口越来越少（**边际收益递减**），
   净收益 = 预期订单收入 − 距离 × 单位里程成本。
5. **指派求解**：把问题建模为最大权二分匹配，同时实现两种策略并对比：
   - `greedy` 贪心：每次取当前净收益最大的组合（基线）
   - `hungarian` 匈牙利算法：O(n³) 全局最优指派
6. **效果评估**：对已完成的调度单，用目标区域目标时段的真实收入与
   「前 3 周同星期同时段基线」对比，得到实际增收并与预期值比较。

> **实验结论（可在论文中直接引用）**：在 200 组/规模、共 6 个规模的随机算例上，
> 匈牙利算法的总净收益稳定优于贪心策略约 **2.5%~2.9%**，
> 在规模 ≥ 12 的算例中 **100% 不劣于且绝大多数严格优于**贪心；
> 代价是计算耗时约为贪心的 3~4 倍，但绝对耗时在 40 个车辆槽位时仍仅约 5.5 毫秒，
> 完全满足实时调度要求。在真实历史数据的单时段算例上两种策略结果相同，
> 说明在这些规模下贪心已足够接近最优。

## 九、常见问题

**Q1：前端提示「无法连接后端服务」**
后端未启动或端口不是 8000。启动后端后刷新页面即可。

**Q2：`pip install` 时 bcrypt 报错**
`requirements.txt` 中已限定 `bcrypt>=3.2,<4.1`，这是 passlib 1.7.4 的兼容区间，
请勿升级到 bcrypt 4.1+。

**Q3：数据库里没有数据，图表都是空的**
执行 `python scripts/seed_data.py`，或在「系统管理 → 数据维护」页面点击「开始生成」。

**Q4：需求预测报错「历史数据不足」**
预测至少需要 14 天历史数据。请用 `seed_data.py --days 60` 生成足够长的数据。

**Q5：想换成 SQLite 快速体验**
在 `backend/.env` 中设置 `DATABASE_URL=sqlite:///./taxi.db` 即可，无需安装 MySQL。

**Q6：修改了业务阈值但不生效**
在「系统管理 → 参数配置」保存后，系统会自动重新载入；
若直接改了 `.env`，需要重启后端服务。
