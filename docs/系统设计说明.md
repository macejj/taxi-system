## 1 项目背景与建设目标

### 1.1 原系统的局限

原「出租车资料管理系统」是一个典型的**档案型 CRUD 应用**，其能力边界可以用一句话概括：把纸质台账搬到网页上。它的具体构成是：

| 维度 | 原系统 | 局限说明 |
| --- | --- | --- |
| 数据模型 | 4 张表：车辆、驾驶员、人车绑定、营运订单 | 没有「区域」这个空间维度，所有统计只能在「全公司」这一粒度上做，无法回答「哪个区域缺车」 |
| 需求侧数据 | 无 | 只记录**已完成的订单**，看不到「有多少乘客没打到车」，运力不足的问题被数据本身掩盖 |
| 运营管理 | 车辆 / 驾驶员的增删改查 + Excel 导入 | 没有保险、营运证、保养等到期管理；没有排班班次概念；没有订单的多条件检索 |
| 数据分析 | 1 个收入折线图 | 无法给出 KPI、满足率、空驶率、时段分布、区域排行、绩效对比等任何可支撑决策的指标 |
| 决策支持 | 无 | 既不能预测未来需求，也不能给出运力投放建议，系统对经营决策的贡献为零 |
| 工程化 | 数据库口令硬编码、无依赖清单、无测试 | 无法交付、无法回归、无法演示 |

### 1.2 升级动因

出租车行业的核心矛盾是**运力在时间与空间上的错配**：早高峰住宅区一车难求，同一时刻商圈却可能有车空驶巡游；平峰期全城运力过剩，高峰期全城运力不足。原系统因为缺少区域维度与需求侧数据，连这个矛盾**描述**不出来，更谈不上**解决**。

因此本次升级围绕一个目标重构系统：**让数据产生决策价值**。具体分解为四条建设线索：

1. **把需求与供给分开记录**——新增 `ride_request`（叫车需求）表，与 `operation_record`（营运订单）并列，使「未被满足的需求」第一次进入系统视野；
2. **把空间维度引入数据模型**——新增 `region`（运营区域）表，让所有统计与决策都能落到「区域 × 时段」的网格上；
3. **把预测与调度做成闭环**——需求预测结果不只是图表，而是写回 `forecast_result` 表、被调度模块直接消费；调度方案下发后还要回收执行反馈并做效果评估；
4. **把算法做成可控可写论文的自研实现**——不黑箱调用第三方库，而是用 numpy 手工实现模型与指派算法，过程可解释、结论可复现（见《核心算法说明》）。

### 1.3 建设目标

| 目标编号 | 目标 | 可验证的完成标志 |
| --- | --- | --- |
| G1 | 建成覆盖「区域—车辆—驾驶员—排班—订单—需求」的完整运营数据底座 | 数据模型扩展为 **12 张表**；一键生成可复现仿真数据（默认 60 天 / 60 车 / 80 名驾驶员），产出约 7.8 万条叫车需求与 6 万条营运订单 |
| G2 | 提供可支撑经营判断的多维数据分析 | **14 个分析接口**，覆盖 KPI 与环比、收入趋势（时/日/周/月）、24 小时供需匹配、星期分布、星期×小时热力图、区域排行与雷达对比、里程利用率、驾驶员绩效、车辆效率、支付方式、天气影响、异常预警 |
| G3 | 提供可量化评估的短时需求预测能力 | **5 个候选模型 + 滚动原点回测自动选优**，输出未来 1~168 小时逐时需求与近似 95% 置信区间，回测指标（MAE/RMSE/MAPE/R²）全量留存 |
| G4 | 提供可执行、可反馈、可评估的调度决策支持 | 区域×时段供需缺口测算 + 贪心/匈牙利双策略指派 + 调度单下发/执行反馈/效果评估全流程闭环 |
| G5 | 达到可交付的工程质量 | 业务参数在线配置并实时生效、操作审计留痕、写操作有业务校验、引擎单元测试与接口冒烟测试全通过 |

## 2 需求分析

| 调度决策 | `FR-DSP-xx` | 9 |

#### 2.1.3 需求预测能力域（FR-FCT）

| 编号 | 需求 | 说明 | 验收标准 |
| --- | --- | --- | --- |
| FR-FCT-01 | 区域可选与数据量提示 | 可选择「全域」或任一功能区做预测，并展示各区域可用于建模的历史需求条数 | 下拉列表首项为「全域（所有区域合计）」，其后按区域编码排序，每项带 `request_count` |
| FR-FCT-02 | 多模型并行建模 | 同时训练均值基线、季节朴素法、季节移动平均、Holt-Winters 三次指数平滑、多元线性回归、逆误差加权组合模型 | `GET /api/forecast/models` 返回 6 个模型的 key 与中文标签；每次预测返回全部候选模型的对比指标 |
| FR-FCT-03 | 滚动原点回测与自动选优 | 以历史末端为原点滚动 3 折，每折直接预测 168 小时，按主指标自动选出最优模型 | 响应中 `folds`=3、`valid_hours`=168、`select_metric` 默认 `rmse`；`metrics` 中 `is_best=true` 的模型与顶层 `model` 字段一致 |
| FR-FCT-04 | 预测输出与置信区间 | 输出未来 1~168 小时逐时预测值及近似 95% 置信区间 | `points` 每项含 `time/value/lower/upper`；下界不为负 |
| FR-FCT-05 | 预测结果留存与回溯 | 每次预测落库形成批次，支持按批次查看明细 | 响应返回 `batch_no`；`GET /api/forecast/history` 列出批次（批次号、模型、区域、步长、MAPE、点数、起止时间）；`GET /api/forecast/batch/{batch_no}` 返回逐点明细 |
| FR-FCT-06 | 预测准确率评估 | 预测目标时刻的真实需求值回填后与预测值对比，按模型给出准确率 | `GET /api/forecast/accuracy?days=N` 返回各模型的样本数、MAE、RMSE、MAPE 与准确率 |
| FR-FCT-07 | 历史数据的显式假设与校验 | 历史不足时拒绝建模并给出可操作的提示 | 历史天数少于 `FORECAST_MIN_HISTORY_DAYS`（默认 14 天）时返回 400，提示补足数据；无任何需求数据时提示先导入或生成运营数据 |

| FR-DSP-05 | 调度方案管理 | 方案列表、详情（含调度指令清单）、状态流转、删除保护 | 列表支持日期区间与状态筛选，附带已完成指令数；状态可用 PATCH 修改；已下发（1）或执行中（2）的方案不可删除 |
| FR-DSP-06 | 调度指令执行反馈 | 对单条调度指令提交执行反馈，驱动方案状态自动收敛 | 反馈状态仅允许 1 执行中 / 2 已完成 / 3 已拒绝 / 4 已取消；终态指令不能重复提交；当方案内所有指令都离开「待执行/执行中」时，方案状态自动置为「已完成」 |
| FR-DSP-07 | 调度效果评估 | 用目标区域目标时段的真实收入与「前 3 周同星期同时段基线」对比，得到实际增收并与预期比较 | 返回方案单量、已完成数、完成率、预期净收益、实际净收益、准确率与逐条明细（含实际收入、基线收入、实际增收、距离） |
| FR-DSP-08 | 策略对比实验与算例基准 | 在真实历史数据上逐时段对比两种策略；在随机算例上做多规模基准实验 | `strategy-compare` 支持 1~72 个整点；`strategy-benchmark` 支持每规模 10~2000 组随机算例，返回各规模的收益均值、提升幅度、更优/持平组数与耗时 |
| FR-DSP-09 | 调度统计 | 按时间范围汇总方案数、指令数、预期净收益、完成/拒绝/待执行数与按日、按策略的分布 | `days` 支持 1~180 天 |

#### 2.1.5 系统管理能力域（FR-SYS）

| --- | --- | --- | --- |
| FR-SYS-01 | 用户与角色管理 | 用户的增删改查、角色分配、状态启停、密码重置 | 角色仅允许 admin / operator / viewer；用户名唯一；不能禁用或删除当前登录账号；内置 `admin` 账号不可删除；用户列表仅管理员可访问 |
| FR-SYS-02 | 身份认证 | 登录签发令牌、获取当前用户、修改本人密码、退出登录 | 登录成功返回 `access_token`、`token_type`、`expires_in`；密码错误返回 400「用户名或密码错误」；账号禁用返回 403；修改密码需校验原密码 |
| FR-SYS-03 | 业务参数在线配置 | 19 项业务参数可在界面修改并实时生效，无需重启 | 参数按分组展示（运营分析 / 调度决策 / 需求预测 / 预警提醒）；修改时按 `value_type` 校验类型，非法值返回 400；保存后立即覆盖运行时配置；另有「重新载入」接口可手动重载 |
| FR-SYS-04 | 操作日志审计 | 自动记录所有写操作；支持查询与清理 | 记录用户名、模块、操作描述、HTTP 方法、路径、IP、状态码、耗时；支持按关键字、模块、天数筛选；清理支持「保留最近 N 天」与「全部清空」 |
| FR-SYS-05 | 数据维护 | 数据量统计、一键生成仿真数据、分级清空业务数据 | 统计返回 11 张业务表的实时行数；仿真生成支持天数（7~365）、车辆数（5~500）、驾驶员数（5~800）、随机种子、是否先清空；清空支持「仅清业务流水」与「连基础档案一起清」两种粒度 |

## 3 系统总体架构

### 3.1 分层架构

系统采用经典的五层架构，**依赖方向自上而下单向传递**，同层之间不互相调用：

```
┌──────────────────────────────────────────────────────────────────────────┐
│ 表现层（Presentation Layer）                                              │
│   Vue 3.5 组合式 API + Vue Router（登录守卫 + 路由懒加载）                  │
│   Element Plus 2.8（表单 / 表格 / 分页 / 标签页 / 反馈）                    │
│   ECharts 5（折线 / 柱状 / 饼图 / 雷达 / 热力图 / 散点 / 仪表盘）           │
│   axios 实例：统一注入 Bearer 令牌、统一错误提示、60 s 超时                  │
│   ↑ 页面（17 个视图）→ api/ 统一接口层 → utils/format.js 字典与格式化        │
└───────────────────────────────┬──────────────────────────────────────────┘
                                │ HTTP / JSON（开发期由 Vite 把 /api 代理到 8000）
┌───────────────────────────────▼──────────────────────────────────────────┐
│ 接口层（API Layer）                                                       │
│   FastAPI 0.110 + Uvicorn，统一前缀 /api，12 个路由模块（78 个路径 / 96 个操作）│
│   ┌────────────────┬────────────────┬────────────────┬─────────────────┐ │
│   │ 认证 auth       │ 驾驶舱 dashboard│ 运营 region/    │ 分析 analysis    │ │
│   │                │                │ vehicle/driver/ │                 │ │
│   │                │                │ assignment/     │                 │ │
│   │                │                │ operation/demand│                 │ │
│   ├────────────────┼────────────────┼────────────────┼─────────────────┤ │
│   │ 预测 forecast   │ 调度 dispatch   │ 系统 system     │                 │ │
│   └────────────────┴────────────────┴────────────────┴─────────────────┘ │
│   中间件：CORS 白名单、操作日志（写操作入库）                              │
│   统一横切：Pydantic 请求/响应校验、依赖注入（鉴权 / 管理员 / 分页）        │

└───────────────────────────────┬──────────────────────────────────────────┘

┌───────────────────────────────▼──────────────────────────────────────────┐
│ 服务层（Service Layer）—— 业务核心                                        │
│   analytics.py  运营分析聚合（KPI、趋势、分布、排行、效率、预警 6 类）      │
│   forecast.py   需求预测引擎（6 个模型 + 滚动原点回测 + 自动选优 + 落库）   │
│   dispatch.py   调度决策引擎（需求估计、运力盘点、缺口、收益矩阵、指派、评估）│
│   simulator.py  仿真数据生成器（区域/车辆/驾驶员/排班/需求/订单，固定种子）  │
└───────────────────────────────┬──────────────────────────────────────────┘
                                │ ORM 会话（每请求一个 Session，用后即关）
┌───────────────────────────────▼──────────────────────────────────────────┐
│ 数据访问层（Data Access Layer）                                           │
│   SQLAlchemy 2.0 Declarative ORM：12 个实体类 + 关系映射 + 复合索引声明     │
```

### 3.2 各层职责与依赖方向

| 层次 | 职责 | 不做什么 | 依赖方向 |
| --- | --- | --- | --- |
| 表现层 | 页面渲染与交互、图表绘制、令牌注入、错误提示、路由守卫、字典与数值格式化 | 不做业务计算，不拼接 SQL，不直接操作数据库 | 只依赖接口层（通过 HTTP） |
| 接口层 | 路由注册与前缀划分、请求参数校验与类型约束、权限依赖注入、分页封装、响应模型声明、异常到状态码的转换 | 不写聚合 SQL，不实现算法 | 只调用服务层与数据访问层 |
| 服务层 | 业务聚合与算法实现：指标计算口径、预测建模与回测、供需缺口与指派、仿真生成 | 不感知 HTTP（不抛 `HTTPException`，用 `ValueError` 表达业务错误，由接口层转换） | 依赖数据访问层 |
| 数据访问层 | 实体与关系定义、索引声明、会话生命周期、方言适配、参数覆盖 | 不含业务判断 | 依赖数据层 |
| 数据层 | 数据持久化、唯一约束、复合索引、聚合下推 | — | — |

> **依赖倒置的实际体现**：服务层的预测与调度引擎被刻意拆成「纯算法层」与「数据装配层」两部分。纯算法层只接受 numpy 数组 / pandas Series，不接触数据库，因此可以脱离 MySQL 单独跑单元测试（`tests/test_forecast.py`、`tests/test_dispatch.py`），这也是「前视泄露检验」「与穷举最优解对比」这类测试得以实现的前提。

### 3.3 一次典型请求的调用链

以「生成调度方案」为例：

```
调度决策中心页面
  → POST /api/dispatch/generate           （表现层，axios 注入 Bearer 令牌）
  → routers/dispatch.py::generate_plan    （接口层：校验 strategy 取值、取当前用户）
  → services/dispatch.py::generate_dispatch_plan
      ├─ pick_peak_hour / peak_hour_in_day   选目标时段
      ├─ build_region_states                 需求估计 + 运力盘点 + 缺口分级
      ├─ _surplus_vehicles / build_gain_matrix   构造净收益矩阵
      ├─ solve_assignment(greedy / hungarian)    双策略求解并对比
      └─ save_plan → models.DispatchPlan / DispatchOrder   （数据访问层落库）
  → schemas.DispatchGenerateResponse      （接口层组装响应）
  → 前端渲染策略对比表与调度指令清单
  ↓ 同时，OperationLogMiddleware 把这次 POST 写入 operation_log 表
```

## 4 功能模块设计

系统共有 14 个功能模块，对应前端 17 个页面与后端 12 个路由模块。以下逐个说明**输入 / 处理 / 输出**。

### 4.1 运营驾驶舱（`dashboard`）

| 项目 | 内容 |
| --- | --- |
| 输入 | 无（总览）；`days`（趋势天数 3~90，默认 14）；`limit`（预警条数 1~50，默认 8）、`days`（预警统计天数 1~30，默认 7） |
| 处理 | 调用分析服务分别取「今日 KPI」「昨日 KPI」「近 7 天 KPI」并计算环比；按状态分组统计车辆与驾驶员；统计最近 6 小时的需求量与完成量；统计待执行/执行中的调度单数量；汇总预警并截断；统计 8 张业务表的行数与数据跨度，判定是否具备预测条件（需 ≥ 14 天） |
| 输出 | 今日 KPI 及 4 项环比（单量、收入、空驶率、满足率）、本周 KPI、车队概况（车辆总数/在营/停运/维修，驾驶员总数/在职/离职/休假）、实时供需窗口（窗口 6 小时、需求量、完成量、满足率）、待办调度单数、更新时间；趋势（收入序列、24 小时供需序列、区域排行前 8）；预警列表与总数；数据健康度（各表行数、最新需求/订单时间、历史天数、是否可预测） |
| 前端 | 60 秒自动刷新；快捷入口卡片跳转到订单、预测、调度页面 |

### 4.2 运营数据分析（`analysis`）

| 项目 | 内容 |
| --- | --- |
| 输入 | 通用日期区间 `start_date` / `end_date`（缺省时按各接口的默认天数回溯，如列表类默认 30 天、需求类默认 7 天、热力图默认按区间折算）；下钻参数 `vehicle_id`、`region_id`、`region_ids`、`top_n`、`sort_by`、`order`、`group_by` |
| 处理 | 全部为**数据库侧聚合**：用 `COUNT/SUM/AVG/COUNT(DISTINCT)` 与 `GROUP BY` 直接得到结果，不在应用层拉全量数据再循环计算；日期区间统一转换为 `[起 00:00, 止次日 00:00)` 的半开区间，避免边界重复计数；比率类指标统一做除零保护；日期截断按方言生成 |

| 关键口径 | 空驶率 = 空驶里程 /(载客里程 + 空驶里程)；满足率 = 已完成需求数 / 叫车需求总数；未满足率 = 状态为「无人接单」或「已取消」的需求数 / 该区域需求总数；收入环比 = (本期 − 上期)/上期，上一期为紧邻的等长区间 |

## 5 关键业务流程

### 5.1 登录与鉴权流程

```
① 用户在登录页输入用户名与口令 → 前端 POST /api/auth/login
② 接口层按用户名查询 sys_user
   ├─ 用户不存在 或 bcrypt 校验失败 → 400「用户名或密码错误」（不区分两者，避免账号枚举）
   └─ 用户存在且口令正确
③ 检查账号状态：status=0 → 403「账号已被禁用，请联系管理员」
④ 生成 JWT：载荷 = { sub: 用户名, role: 角色, exp: 当前时间 + 有效期(默认 1440 分钟) }
   使用 HS256 与 SECRET_KEY 签名
⑤ 更新 last_login，返回 { access_token, token_type: "bearer", expires_in }
⑥ 前端把令牌写入 localStorage；axios 请求拦截器为后续每个请求加上
   Authorization: Bearer <token>
```

后续每个受保护请求的鉴权链路：

```
请求进入
  → OAuth2PasswordBearer 从 Authorization 头取令牌（auto_error=False，缺失则交由业务判断）
  → get_current_user 依赖：
       ├─ 无令牌 → 401「登录状态无效或已过期，请重新登录」（带 WWW-Authenticate: Bearer）
       ├─ jwt.decode 失败（签名错误 / 过期 / 格式非法）→ 401
       ├─ 载荷无 sub → 401
       ├─ 按 sub 回查用户表，查不到 → 401
       └─ user.status != 1 → 403「账号已被禁用，请联系管理员」
  → 若该接口额外依赖 require_admin：
       └─ role != "admin" → 403「无权限执行该操作（需要管理员）」
  → 进入业务处理
```

要点说明：

- **令牌是无状态的**，退出登录由前端清除本地令牌完成（后端 `/api/auth/logout` 仅返回成功消息），因此服务端不维护令牌黑名单；
- **禁用账号立即失效**：由于每次鉴权都会回查用户表，把用户状态改为禁用后，其已签发的令牌在下一次请求就会被拒绝；
- 前端路由守卫只判断本地是否存在令牌，令牌是否仍然有效由后端 401 决定；收到 401 时前端清除令牌并跳回登录页，同时带上 `redirect` 参数以便登录后回到原页面。

### 5.2 运营数据接入流程

系统有 **3 条**数据接入路径，它们最终都要经过同一套「派生字段计算」逻辑，保证统计口径一致。

**路径 A：手工录入（`POST /api/operation/`）**

```
① 校验订单号：未提供则按时间戳自动生成；已存在 → 400「订单号已存在」
② 校验外键：车辆不存在 → 400「车辆不存在」；驾驶员不存在 → 400「驾驶员不存在」
③ 派生字段计算 derive_fields：
     stat_date        = 上车时间的日期
     hour             = 上车时间的小时（0~23）
     weekday          = 上车时间的星期（0=周一）
     is_peak          = 是否落在早高峰 7:00–9:00 或晚高峰 17:00–19:00
     duration_minutes = (下车时间 − 上车时间) 的分钟数
     avg_speed        = 载客里程 ÷ (时长/60)，时长为 0 时取 0
     若下车时间早于上车时间 → 400「下车时间不能早于上车时间」
④ 写入 operation_record，返回补齐了车牌、驾驶员姓名与上下车区域名称的记录
```

修改订单时同样会重算派生字段：先把未提交的字段与既有值合并，再对合并结果重算，然后写回 5 个派生字段，避免出现「改了时间但统计口径没变」的脏数据。

**路径 B：Excel 批量导入（`POST /api/operation/import-excel`）**

```
① 读取上传文件（openpyxl 解析），解析失败 → 400「文件解析失败：<原因>」
② 校验必要列：order_no / vehicle_plate / driver_name / start_time / end_time /
   loaded_mileage / empty_mileage / amount
   缺列 → 400「缺少必要列：...。请先下载导入模板。」
③ 一次性把文件中出现的车牌、驾驶员姓名、区域名称批量查出，建立内存映射
   （避免逐行查库造成 N+1 查询）
④ 一次性查出文件中已存在的订单号，用于判重
⑤ 逐行校验（行号按 Excel 实际行号给出，含表头）：
     order_no 为空或为 nan            → 计入错误行
     order_no 已存在或文件内重复       → 计入重复数
     vehicle_plate 未登记              → 计入错误行
     driver_name 未登记                → 计入错误行
     时间无法解析 / 下车早于上车        → 计入错误行
   通过的行执行派生字段计算后进入待插入缓冲
⑥ 缓冲每满 2000 条批量插入一次，最后再冲刷一次
⑦ 返回 ImportResult：total_rows / imported / duplicated / error_rows / error_messages
```

**路径 C：仿真生成（`POST /api/system/data/simulate`）**

```
① 可选清空：按顺序删除调度指令 → 调度方案 → 预测结果 → 营运订单 → 叫车需求 → 人车绑定
   （include_master=true 时继续删除车辆 → 驾驶员 → 区域）
② 生成 10 个功能区（交通枢纽、商圈、居民区、学校、景区、医院、工业区），
   各自带中心经纬度、面积与需求强度等级
③ 按各区域需求量占比分配车辆常驻区域，叠加 ±20% 结构性偏差，
   使部分区域长期偏紧、部分长期偏松，为调度决策提供真实对象
④ 生成驾驶员档案（评分服从截断正态、投诉与违章次数服从泊松分布）
⑤ 建立人车绑定与班次：每车至少 1 名在职驾驶员，约 25% 车辆配双班司机
⑥ 需求规模自动标定：以「平均在岗车辆数 × 单车小时服务能力 × 目标负荷率 0.85」
   反推逐小时目标需求量，再按各区域需求强度与作息形态分摊
⑦ 逐日逐小时生成：
     需求量 λ = 基准量 × 城市小时曲线 × 区域作息形态 × 星期系数
               × 天气系数 × 节假日系数 × 缓慢增长趋势
     需求量 ~ 泊松(λ)
     对每一单需求：按该区域该小时「在岗车辆数 × 单车小时服务能力 ÷ 需求」的比例
       决定是否被满足；满足则同时写入叫车需求（状态=已完成）与营运订单（含里程、
       时长、金额、支付方式、天气），未满足则只写叫车需求（状态=无人接单或已取消）
⑧ 每 6000 条或每日结束落盘一次，并把当日行驶里程累加到车辆累计里程
⑨ 返回各表生成条数与总耗时
```

> 三条路径的共同点：只要数据要进入 `operation_record`，就必须先经过 `derive_fields`。这是「预计算冗余字段」策略能够成立的前提。

### 5.3 需求预测流程

```
① 数据聚合（load_hourly_demand）
   按 (stat_date, hour) 对 ride_request 分组计数 → (日期, 小时) → 需求量
   以最小与最大时刻为界生成完整小时索引，缺失小时补 0，同时聚合出每小时
   的「是否存在节假日」「是否存在雨雪天气」两个标记位
   （数据源必须是叫车需求而非营运订单：后者只反映被满足的需求，
     运力不足时会系统性低估真实需求）

② 前置校验
   序列为空            → 400「暂无历史叫车需求数据，请先导入或生成运营数据」
   历史天数 < 14 天     → 400「历史数据仅 X 天，不足 14 天，无法可靠建模」
   horizon 不在 1~168  → 400「预测时长需在 1~168 小时之间」

③ 特征构造（build_features）
   hour（0~23）、weekday（0~6，0=周一）、is_peak（是否早晚高峰）、
   is_holiday（节假日）、rain（雨雪天气）
   对未来的时刻，is_holiday 与 rain 按「未知」取 0

④ 滚动原点回测（rolling_backtest）
   验证窗口 V = 168 小时（7 天），折数 F = 3
   第 f 折：训练集 = 序列前 n−fV 个点，预测原点 = n−fV，测试集 = 其后 V 个点
   每个模型从预测原点**直接**预测未来 V 小时（回看步长 ≥ V，不使用预测窗口内真值）
   所有折的预测值与真值拼接后统一计算 MAE / RMSE / MAPE / R²

⑤ 模型库并行训练
   均值基线（仅参照，不参与组合与选优）、季节朴素法、季节移动平均、
   Holt-Winters 三次指数平滑（阻尼趋势）、多元线性回归、逆误差加权组合模型

⑥ 自动选优
   按主指标（默认 RMSE，可配置为 mae / mape）升序排序，
   排除均值基线后取最优模型，并在指标表中标记 is_best

⑦ 输出预测
   最优模型在**全部历史数据**上重新训练，预测未来 horizon 小时
   以回测残差标准差 σ 给出近似 95% 置信区间：ŷ ± 1.96σ(1+0.01h)，下界截断到 0
   同时取历史最后 7 天（168 点）作为对照曲线

⑧ 落库（_save_forecast）
   生成批次号 FC + 时间戳 + 随机三位数
   逐点写入 forecast_result（批次号、区域、目标时刻、目标日期、小时、模型名、
   预测值、上下界、回测 MAPE、步长、创建人）

⑨ 结果消费
   · 前端展示模型对比表、预测曲线、准确率评估与历史批次回溯
   · 调度决策模块以「区域 × 星期 × 小时」的历史均值作为轻量需求估计
     （完整预测引擎单区域耗时 0.5~1 s，无法满足 24 小时 × 10 区域的交互式遍历）
   · 目标时刻过去后，真实需求值回填到 actual_value，用于计算预测准确率
```

### 5.4 调度决策流程

```
① 时段选择
   · 指定了 target_hour → 直接使用；未指定 plan_date 时默认取当天（23 点后顺延到次日）
   · 未指定 target_hour 且未指定日期 → 在未来 24 个整点中自动择优
   · 未指定 target_hour 但指定了日期 → 在该日剩余整点中自动择优
   择优准则：可再分配量 = min(Σ max(缺口,0), Σ max(−缺口,0)) 最大
   （若按「总缺口最大」选，会选到全城普遍缺车的高峰时段，而该时段没有任何
     运力可以调过去，方案必然为空）

② 需求估计（区域 × 星期 × 小时）
   D(j,t) = 近 4 周同星期同时段的历史平均请求数 × 近期趋势修正系数
   趋势修正系数 = clip(近 7 天需求总量 ÷ 前 7 天需求总量, 0.7, 1.4)

③ 运力盘点
   可用运力 S(j) = 常驻区域为 j 且状态为「在营」的车辆数
                   − 已被「已下发/执行中」且覆盖目标时段的调度单占用的车辆数
                   （下限为 0）
   折算运力 C(j) = S(j) × 单车小时服务能力（默认 1.5 单/(车·小时)）

④ 缺口测算与分级
   缺口 g(j) = D(j) − C(j)
   g ≤ 0                  → 运力盈余
   0 < g/D < 0.15         → 轻微缺口
   0.15 ≤ g/D < 0.40      → 明显缺口
   g/D ≥ 0.40             → 严重缺口

⑤ 收益矩阵构造
   对缺口区域 j 的第 k 辆车：可承接订单数 o(j,k) = min(ρ, max(0, g(j) − (k−1)ρ))
     （第一辆车承接 min(ρ, g)，第二辆承接剩下的……直到缺口填满）
   该槽位预期收入 R(j,k) = o(j,k) × 区域近 30 天平均订单金额
   单车调度成本 C(i,j) = 距离 × 单位里程成本（默认 1.80 元/公里）
     距离 = 1.35 × 区域中心点之间的球面距离
   净收益 G(i,(j,k)) = R(j,k) − C(i,j)，只保留 G > 最小可接受净收益（默认 5 元）的组合
   可调出车辆数上限 10 辆/区域，可调入槽位上限 8 个/区域

⑥ 指派求解
   建模为最大权二分匹配：每辆车最多执行一个调度、每个槽位最多接收一辆车
   同时求解两种策略用于对比：
     greedy    —— 按净收益降序依次占用未被使用的行与列
     hungarian —— O(N³) 全局最优指派（先把 G ≤ 0 的元素裁剪为 0，再补成方阵）

⑦ 方案组装与落库
   方案号 = DP + 调度日期 + 两位时段 + 随机三位数
   调度单号 = 方案号 − 三位序号；按「优先级升序、净收益降序」重排后重新编号
   优先级：严重缺口=1、明显缺口=2、其余=3
   写库：先写 dispatch_plan（日期、时段、策略、需求估计方法、总需求、总运力、
   总缺口、调度车辆数、预期净收益、状态=草稿），再逐条写入 dispatch_order
   若采用策略非法则回退为匈牙利并追加告警；无可调度组合时给出明确 warning

⑧ 下发执行
   方案状态 PATCH 修改为「已下发(1)」→ 执行中(2)
   执行人对每条调度单提交反馈：执行中(1) / 已完成(2) / 已拒绝(3) / 已取消(4)
   终态调度单不可重复反馈；当方案内所有调度单都不再处于「待执行/执行中」时，
   方案状态自动置为「已完成(3)」

⑨ 效果评估
   对每条调度单：
     实际收入 = 目标区域在目标日期目标时段（1 小时）内的营运订单收入合计
     基线收入 = 前 1/2/3 周同一星期同一时段的收入均值
     实际增收 = (实际收入 − 基线收入) ÷ 该区域本次调度车辆数 − 该单预期成本
   方案实际净收益 = 所有「已完成」调度单的实际增收之和
   方案准确率 = max(0, 100 − |实际净收益 − 预期净收益×已完成占比| ÷ 预期净收益 × 100)
   返回逐条明细，便于定位「哪一条调度没有达到预期」
```

### 5.5 预警产生流程

预警由分析服务的 `abnormal_alerts(db, days)` 统一汇总，共 **6 类**，全部在查询时动态计算，不落库：

```
① 区域未满足率过高
   条件：该区域近 days 天需求量 ≥ 50 且未满足率 ≥ UNFULFILLED_RATE_WARN（默认 15%）
   等级：未满足率 ≥ 30% → high，否则 medium
   建议：在高峰时段向该区域调度运力，或增加该区域排班车辆

② 车辆空驶率偏高
   条件：该车近 days 天完成 ≥ 10 单，且空驶里程占比 > EMPTY_RATE_WARN（默认 40%）
   等级：medium
   建议：优化接单区域与巡游路线，减少空驶

③ 收入环比下滑
   条件：近 days 天总收入相对「紧邻的等长上一周期」降幅超过 INCOME_DROP_WARN（默认 −20%）
   等级：high
   建议：结合时段与区域需求分析，调整运力投放与排班结构

④ 车辆证照与保养到期（三类，逐车检查）
   保险到期日 ≤ 今天 + INSURANCE_WARN_DAYS（默认 30 天）
   营运证到期日 ≤ 今天 + CERT_WARN_DAYS（默认 30 天）
   下次保养日 ≤ 今天 + MAINTENANCE_WARN_DAYS（默认 15 天）
   等级：已过期 → high，即将到期 → medium
   （只检查状态不为「停运」的车辆）

⑤ 驾驶证到期
   条件：在职驾驶员的驾驶证有效期 ≤ 今天 + LICENSE_WARN_DAYS（默认 30 天）
   等级：已过期 → high，即将到期 → medium

⑥ 在营车辆长时间无营运记录
   条件：状态为「在营」的车辆在近 days 天没有产生任何营运订单
   等级：数量 < 5 台 → low，否则 medium
   建议：核实车辆是否实际停运，必要时调整车辆状态或安排上线

⑦ 排序与输出
   按等级 high → medium → low 排序，同等级内按预警数值绝对值降序
   每条预警包含：level、type、target、title、content、value、unit、suggestion
   · 驾驶舱取前 N 条（默认 8 条）
   · 运营分析的「异常预警」页签取全量并支持按等级筛选与关键字搜索
```

> 设计取舍：预警**不落库**，每次查询按当前阈值实时计算。好处是调整阈值后立即生效、不会残留历史误报；代价是查询开销随数据量增长，因此各接口都对统计天数做了上限约束（驾驶舱 1~30 天、运营分析 1~90 天）。

> 与预警相关的写操作审计流程（所有写操作如何落进 `operation_log`）见 7.5 节。

### 6.1 为什么预测算法用 numpy 手工实现而不引入 scikit-learn

这是本项目一个**刻意的工程决策**，理由有四条，按重要性排序：

1. **论文需要「可解释的实现」，而不是「库的调用」。** 毕业设计的算法章节必须能写清楚模型的状态递推式、参数寻优方式、回测折数与评价口径。若调用 `statsmodels.tsa.holtwinters.ExponentialSmoothing`，论文只能写「调用了某函数、设置了某几个参数」，算法过程成为黑箱；而手工实现意味着水平/趋势/季节三重递推、阻尼系数的求和公式、季节模式（加法/乘法）的选取条件、参数网格的搜索范围，全部由项目自己定义并可写入论文。
2. **必须能控制「多步直接预测」与「无前视泄露」这两个关键约束。** 通用库的默认接口通常面向「单步滚动预测」（predict one step, observe, predict next），而这正是需求预测中最容易产生前视泄露的写法。本项目的做法是：**每个模型都从预测原点一次性直接预测未来 168 小时，回看步长不小于预测步长**（季节朴素法回看 168 小时、移动平均回看 3×168 小时），从而在结构上杜绝窥探预测窗口。这一点由 `tests/test_forecast.py::test_no_lookahead` 守卫——把预测窗口中段数据篡改为 9999，若预测值发生变化即判定泄露。要用库实现同等保证，反而需要绕开其默认流程，复杂度并不更低。
3. **消除重型科学计算库的部署与兼容风险。** scikit-learn 会连带引入 scipy 等编译型依赖，在不同 Python 版本（尤其是较新版本）与不同操作系统上存在安装失败或二进制不兼容的风险；本项目的依赖清单因此只保留 `numpy / pandas / openpyxl`，其中 numpy 与 pandas 是数据分析本身不可或缺的，而 scikit-learn 的功能在需求规模（1440 个观测点、6 个模型、3 折回测）下用不到百行 numpy 代码即可覆盖。实测一次完整预测（含 3 折回测 × 6 个模型）约 **0.7 秒**，性能完全够用。
4. **调度侧的指派算法同样需要「能对比、能验证」。** 匈牙利算法与贪心策略都是手工实现，因此可以：① 用**穷举法**在 20 组随机小矩阵上验证匈牙利解与全局最优解完全一致；② 在同一套收益矩阵上公平对比两种策略的收益与耗时（规模 4~40 各 200 组算例）。这些实验结论（匈牙利稳定优于贪心约 2.5%~2.9%、N=40 时耗时 5.6 ms）是论文实验章节的核心素材，而直接调用 `scipy.optimize.linear_sum_assignment` 则无法做同源对比，也讲不清「为什么先要把负收益裁剪为 0」。

> 一句话总结：**在这个项目的数据规模下，`numpy` 手工实现的收益（可解释、可控制、可对比、零额外部署风险）远大于成本（约数百行代码），而 scikit-learn 的主要优势（算法覆盖面、大规模数据上的工程优化）在本项目中恰好用不上。**

## 7 系统安全设计

### 7.1 口令存储：bcrypt 单向散列

| 项目 | 设计 |
| --- | --- |
| 算法 | bcrypt（通过 passlib 的 `CryptContext` 管理），配置 `schemes=["bcrypt"], deprecated="auto"` 以便将来平滑更换算法 |
| 加盐 | bcrypt 自动为每个口令生成独立盐值并编码进散列串，无需额外维护盐字段 |
| 存储字段 | `sys_user.password_hash`，长度 100 字符，可容纳 bcrypt 输出（约 60 字符） |
| 超长口令处理 | 写入前按 bcrypt 的 72 字节上限截断（`password[:72]`），避免底层库直接抛错 |
| 校验容错 | 校验函数捕获所有异常并返回 `False`，防止散列串格式损坏时把异常抛到接口层 |
| 口令复杂度 | 由 Pydantic 约束：长度 4~64 字符（`UserLogin` / `UserCreate` / `PasswordReset` / `PasswordChange` 一致） |
| 明文不可回显 | 所有用户相关响应模型（`UserOut`）**不包含** `password_hash` 字段 |
| 修改口令 | 必须先校验原口令，错误返回 400「原密码不正确」 |
| 重置口令 | 仅管理员可执行，重置后返回消息提示 |

更新途径一览：登录口令错误信息统一为「用户名或密码错误」，**不区分「用户不存在」与「口令错误」**，避免账号枚举。

### 7.2 令牌与会话

| 项目 | 设计 |
| --- | --- |
| 令牌类型 | JWT，算法 HS256，密钥来自 `SECRET_KEY` 配置（`.env.example` 中明确注明「生产环境务必修改为随机长字符串」） |
| 载荷 | `sub`（用户名）、`role`（角色）、`exp`（过期时间） |
| 有效期 | `ACCESS_TOKEN_EXPIRE_MINUTES` 默认 **1440 分钟（24 小时）**；登录响应的 `expires_in` 以秒为单位返回，供前端提示 |
| 传递方式 | 请求头 `Authorization: Bearer <token>`，由 `OAuth2PasswordBearer` 解析 |
| 失效判定 | 令牌缺失 / 签名错误 / 已过期 / 载荷缺 `sub` / 用户不存在 → 统一 401「登录状态无效或已过期，请重新登录」，并附带 `WWW-Authenticate: Bearer` |
| 账号禁用 | 每次鉴权都回查 `sys_user`，`status != 1` 时返回 403，**已签发令牌立即失效** |
| 退出登录 | JWT 无状态，退出由前端清除本地令牌实现；后端接口仅返回成功消息 |
| 前端处理 | 收到 401 时清除本地令牌、跳转登录页并记录 `redirect`，提示「登录已过期，请重新登录」 |

**实现方式**

权限采用**两级强制校验 + 一层集中式守卫**的结构：

1. `get_current_user`：要求登录，覆盖除 3 个公开接口（`POST /api/auth/login`、`GET /`、`GET /api/health`）之外的全部操作。
2. `require_admin`：要求管理员，96 个操作中有 **10 个**依赖它，全部集中在系统管理模块 ——
   用户列表 / 新增用户 / 修改用户 / 重置密码 / 删除用户、修改参数配置、重新载入参数配置、
   清空操作日志、生成仿真数据、清空业务数据。
3. `ReadOnlyGuardMiddleware`（`core/permission.py`）：**只读角色守卫中间件**。
   对所有 `/api` 下的 `POST / PUT / PATCH / DELETE` 请求解析 JWT 中的 `role`，
   若为 `viewer` 则直接返回 403，并给出明确提示
   「当前账号为只读用户（viewer），只能查看数据，不能执行新增/修改/删除操作」。
   登录、退出、修改本人密码三个接口在放行白名单中，否则只读账号无法登录或改密。

> **为什么用中间件而不是给每个接口加 `Depends(require_writer)`？**
> 逐个接口加依赖时，只要将来新增接口忘记挂依赖就会产生权限漏洞；
> 用中间件是 **fail-safe** 的 —— 默认拒绝，只有显式列入白名单的路径才放行。
> 中间件与操作日志中间件共用同一套令牌解析逻辑（`core/security.decode_token_claims`），
> 并且**注册顺序刻意安排为日志中间件在外层**，
> 使被拒绝的越权写请求同样会写入 `operation_log`，便于安全审计。

**前端配合**：`Layout.vue` 在加载当前用户后把 `role` 写入 `localStorage`，
当角色为 `viewer` 时在内容区顶部显示常驻提示条，说明「可以查看全部数据，但写操作会被拒绝」；
`system/UserManage.vue` 与 `system/DataMaintain.vue` 另有 `isAdmin` 级别的按钮禁用。
需要强调的是：**前端的按钮禁用只是体验优化，真正的权限边界始终在后端**。

### 7.6 删除操作的关联数据保护

系统对基础档案的删除一律采用**「先检查引用，再决定是否允许删除」**的策略，宁可拒绝也不产生孤儿数据：

| 删除对象 | 检查规则 | 拒绝时的提示 | 替代方案 |
| --- | --- | --- | --- |
| 区域 | 是否被营运订单引用（作为上车**或**下车区域） | 「该区域已关联 N 条营运记录，无法删除；可将其状态改为停用」 | 改为停用（`status=0`） |
| 区域 | 是否被叫车需求引用 | 「该区域存在叫车需求数据，无法删除；可将其状态改为停用」 | 改为停用 |
| 车辆 | 是否已产生营运记录 | 「该车辆已产生 N 条营运记录，不能删除；可将状态改为停运」 | 改为停运（`status=0`）或维修（`status=2`） |
| 车辆（可删除时） | — | — | 先清理其 `vehicle_driver` 绑定关系，再删除车辆 |
| 驾驶员 | 是否已产生营运记录 | 「该驾驶员已产生 N 条营运记录，不能删除；可将状态改为离职」 | 改为离职（`status=0`）或休假（`status=2`） |
| 驾驶员（可删除时） | — | — | 先清理其 `vehicle_driver` 绑定关系，再删除驾驶员 |
| 人车绑定 | — | — | **不做物理删除**：置 `status=0` 并写入 `unassign_date`，保留排班历史 |
| 调度方案 | 状态是否为「已下发(1)」或「执行中(2)」 | 「已下发或执行中的方案不能删除」 | 先把状态改为「已取消(4)」再删除 |
| 调度方案（可删除时） | — | — | 其下调度指令由 ORM 关系配置 `cascade="all, delete-orphan"` 级联删除 |
| 用户 | 是否为当前登录账号；是否为内置 `admin` | 「不能删除当前登录账号」/「内置管理员账号不能删除」 | 改为禁用（`status=0`） |
| 营运订单 / 叫车请求 | — | — | 允许删除（属于流水数据，删除不影响档案完整性） |

其他相关的数据完整性约束：

- **唯一约束**：区域编码、车牌号、驾驶员身份证号、订单号、请求编号、方案编号、调度单号、用户名、配置键均由数据库唯一约束 + 应用层预检查双重保证；
- **外键约束**：`vehicle_driver`、`ride_request`、`operation_record`、`dispatch_order` 均通过 `ForeignKey` 引用基础档案，防止写入悬空引用；
- **状态而非删除**：车辆、驾驶员、区域、用户、人车绑定五类实体都提供「停用/离职/解绑/禁用」状态，业务上以状态流转替代删除，从而让历史统计口径始终完整。

### 8.3 部署步骤

**（1）初始化数据库**

```bash
# 方式一：MySQL（默认 root/123456789@localhost:3306/taxi_db）
cd backend
copy .env.example .env          # Windows
# cp .env.example .env          # macOS / Linux
# 编辑 .env 修改 DB_USER / DB_PASSWORD / DB_NAME / SECRET_KEY

python scripts/init_db.py       # 建表 + 初始化 3 个演示账号 + 补齐 19 项系统参数

# 方式二：无 MySQL 环境，改用 SQLite
# 在 backend/.env 中设置：DATABASE_URL=sqlite:///./taxi.db
```

`init_db.py` 执行后会打印建表结果（12 张表）、系统参数新增项数，以及三个演示账号的创建情况。加 `--reset` 参数可先删表重建（需手工输入 `yes` 确认）。

**（2）生成仿真数据**

```bash
python scripts/seed_data.py                                  # 默认近 60 天 / 60 台车 / 80 名驾驶员
python scripts/seed_data.py --days 90 --vehicles 80 --drivers 100   # 自定义规模
```

也可在启动服务后，通过「系统管理 → 数据维护」页面一键生成（等价于调用 `POST /api/system/data/simulate`，参数含义一致）。

**（3）启动后端服务**

```bash
python -m uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

启动时的 `lifespan` 会执行两件事：`Base.metadata.create_all` 确保 12 张表存在，然后 `ensure_defaults` 补齐系统参数并把库中配置覆盖到运行时配置单例。

- 接口文档（Swagger UI）：<http://localhost:8000/docs>
- 备用接口文档（ReDoc）：<http://localhost:8000/redoc>
- 健康检查：<http://localhost:8000/api/health>
- 服务信息：<http://localhost:8000/>

**（4）启动前端**

```bash
cd frontend
npm install
npm run dev
```

浏览器访问 <http://localhost:5173>。Vite 已把 `/api` 代理到 `http://localhost:8000`，开发期无需处理跨域。
